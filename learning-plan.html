How to use this plan

Read this once before you start — it will save you a lot of confusion later.

Each week has the same rhythm: a short Learn block that explains the concept, a Build block where you write code, and a Checklist you tick off as you go. The checkboxes drive the progress bar at the top. Tick a box when you have actually done the thing, not just read about it — the whole point of the balanced format is that understanding sticks when you build.

Your progress saves to a file. Open this page from your repo in Chrome or Edge, click Link PROGRESS.md at the top, and pick that file once. From then on every checkbox you tick is written straight into PROGRESS.md and read back when you reopen the page — so your progress is real, versionable in git, and survives refreshes. (Other browsers can still use the checklist; the file-writing step needs Chrome or Edge.)
A note on model names and versions. The code below uses current identifiers (for example claude-opus-4-8 style model aliases and the Agent SDK package name). Anthropic ships changes often, so if an import or model name ever fails, open the linked official doc for that topic — it is always the source of truth. Every external link in this plan points at Anthropic's own documentation.

One-time setup

Do this before Week 1. It should take under an hour.

  • Install Node.js 20 LTS or newer. Check with node --version. The SDKs require Node 20+.
  • Get an API key. Create one in the Claude Console, then add a little credit. Learning agents costs real (small) money because every tool call is an API call — budgeting a few dollars is plenty for this whole plan.
  • Store the key safely. Put it in an environment variable named ANTHROPIC_API_KEY. Never commit it to git. Both SDKs read this variable automatically.
  • Create a practice repo. One folder, git init, a .gitignore with node_modules and .env in it. You'll add a subfolder per week.
Want to skip the typing? Download the ready-made starter repo — the same scaffold described below, with a runnable week1/hello.ts, all seven week folders, package.json, tsconfig.json, .env.example, and a PROGRESS.md tracker. Unzip it, then jump straight to installing dependencies.

Version control & push to GitHub

The scaffold is ready to become its own repository — it already includes a .gitignore that excludes node_modules/, dist/, and .env, so your API key never enters git history. Run these inside the claude-agents-course folder, not its parent:

Run git status afterward to confirm you see the week folders and config files — but not .env or node_modules/. Then pick one way to get it onto GitHub.

Option A — GitHub CLI (fewest steps). The gh tool creates the remote repo and pushes in a single command. Install it if you don't have it (winget install GitHub.CLI on Windows, brew install gh on macOS), sign in once, then run both commands:

The single most important thing to understand first

There are two different SDKs, and knowing which is which prevents 90% of beginner confusion.

Client SDK

@anthropic-ai/sdk

The low-level library that talks to the Messages API. You send messages, you get a response. If you want tools, you write the loop that runs them and feeds results back.

  • Maximum control, minimum magic
  • You implement the "agent loop" by hand
  • Best for learning how agents actually work
  • Weeks 1–2 live here

Agent SDK

@anthropic-ai/claude-agent-sdk

The high-level library that runs the full agent loop for you — the same engine that powers Claude Code. Built-in tools, permissions, subagents, and skills all come included.

  • The loop, tools, and context management are done for you
  • Where tools, skills, and subagents officially live
  • Best for building real agents
  • Weeks 3–7 live here

The plan deliberately starts with the Client SDK for two weeks. Building one tool loop by hand — even a clumsy one — is the fastest way to truly understand what the Agent SDK is doing for you. After that, you switch to the Agent SDK and never look back.

Week1

Foundations & your first Claude call

Get comfortable talking to the model with the Client SDK.

0/5
Learn

Understand the shape of a request to Claude: a model, a max_tokens budget, and a list of messages with roles (user / assistant). The response comes back as an array of content blocks — for now they'll all be text, but this block structure is exactly what makes tools and thinking possible later. Read about the message structure and streaming; don't skip streaming, since agents feel unusable without it.

Build — a talking script

Create week1/hello.ts. Make a single call, print the text, then upgrade it to stream token-by-token.

import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic(); // reads ANTHROPIC_API_KEY from the env

const message = await client.messages.create({
  model: "claude-opus-4-8",
  max_tokens: 1024,
  messages: [{ role: "user", content: "Explain what an AI agent is in 3 sentences." }],
});

for (const block of message.content) {
  if (block.type === "text") console.log(block.text);
}

Then swap in the streaming helper and watch the difference:

const stream = client.messages
  .stream({
    model: "claude-opus-4-8",
    max_tokens: 1024,
    messages: [{ role: "user", content: "Say hello, one word at a time." }],
  })
  .on("text", (text) => process.stdout.write(text));

await stream.finalMessage();

Week2

Tool use — build the agent loop by hand

The core idea behind every agent, written out yourself once.

0/5
Learn

An "agent" is mostly one loop: you give the model a set of tools (name + description + JSON input schema); the model replies with a tool_use block asking you to run one; your code runs it and sends the answer back as a tool_result; you repeat until the model stops asking for tools and gives a final answer. That's the whole trick. Learn to recognize stop_reason: "tool_use" — it's the signal to run a tool and loop again.

Build — a weather-ish agent

Create week2/tool-loop.ts. Define one fake tool, then write the loop that services it. Keep the "tool" a hardcoded function for now — the point is the loop, not the data.

import Anthropic from "@anthropic-ai/sdk";
const client = new Anthropic();

const tools = [{
  name: "get_weather",
  description: "Get the current temperature for a city.",
  input_schema: {
    type: "object",
    properties: { city: { type: "string" } },
    required: ["city"],
  },
}];

// your real "tool" — just a function
function getWeather(city: string) {
  return `It is 21°C and sunny in ${city}.`;
}

const messages: Anthropic.MessageParam[] = [
  { role: "user", content: "What's the weather in Lisbon?" },
];

// the agent loop
while (true) {
  const res = await client.messages.create({
    model: "claude-opus-4-8",
    max_tokens: 1024,
    tools,
    messages,
  });
  messages.push({ role: "assistant", content: res.content });

  if (res.stop_reason !== "tool_use") {
    const text = res.content.find((b) => b.type === "text");
    if (text && text.type === "text") console.log(text.text);
    break; // model is done
  }

  // run every tool the model asked for, collect results
  const results: Anthropic.ToolResultBlockParam[] = [];
  for (const block of res.content) {
    if (block.type === "tool_use" && block.name === "get_weather") {
      const { city } = block.input as { city: string };
      results.push({
        type: "tool_result",
        tool_use_id: block.id,
        content: getWeather(city),
      });
    }
  }
  messages.push({ role: "user", content: results });
}
Payoff moment. Once this runs, you have written, from scratch, the exact pattern the Agent SDK automates. Everything in Weeks 3–7 is a more capable version of this loop. Keep this file — you'll appreciate it later.

Week3

The Agent SDK — let the loop run itself

Switch to the high-level SDK and define your own tools cleanly.

0/6
Learn

Now install @anthropic-ai/claude-agent-sdk. The entire loop you wrote by hand becomes a single query() call that returns an async stream of messages. You get built-in tools (reading and writing files, running commands, web search) for free, and you define your own tools with the tool() helper — which uses Zod schemas so your inputs are type-safe — bundled into an in-process server via createSdkMcpServer(). Learn the key options: systemPrompt, allowedTools (auto-approve tools so they don't prompt), mcpServers, maxTurns, and permissionMode.

Build — the same idea, one tenth the code
import { query, tool, createSdkMcpServer } from "@anthropic-ai/claude-agent-sdk";
import { z } from "zod";

// define a custom tool, type-safe via Zod
const weather = tool(
  "get_weather",
  "Get the current temperature for a city.",
  { city: z.string() },
  async ({ city }) => ({
    content: [{ type: "text", text: `It is 21°C and sunny in ${city}.` }],
  })
);

const myTools = createSdkMcpServer({
  name: "my-tools",
  tools: [weather],
});

for await (const msg of query({
  prompt: "What's the weather in Lisbon, and save it to weather.txt?",
  options: {
    model: "claude-opus-4-8",
    mcpServers: { "my-tools": myTools },
    allowedTools: ["mcp__my-tools__get_weather", "Write"],
    maxTurns: 6,
  },
})) {
  if ("result" in msg) console.log(msg.result);
}
Notice what you did not write: no loop, no stop_reason check, no manual tool_result plumbing, and the model could also use the built-in Write tool to create a file — all from one prompt. That's the Agent SDK earning its keep.

You've now met tools from both sides: hand-rolled last week, and a clean custom tool() here. Next week is a dedicated deep-dive on the full tool landscape — the built-in catalog, connecting external MCP servers, and how to control exactly what an agent is allowed to touch.

Week4

Tools in depth — the agent's hands

The three sources of tools, how to design them, and how to control what an agent can touch.

0/7
Learn

You've met tools twice already — hand-rolled in Week 2, and a clean custom tool() in Week 3. This week zooms out to the whole picture. In the Agent SDK, an agent's tools come from three places, and knowing the distinction is what lets you assemble capable agents deliberately instead of by luck:

  • Built-in tools — ship with the SDK; the same ones that power Claude Code. File operations (Read, Write, Edit), a shell (Bash), search (Glob, Grep), the web (WebSearch, WebFetch), notebooks (NotebookEdit), and orchestration tools you'll meet soon (Agent for subagents, Skill, TodoWrite). You get these for free — you just decide which to allow.
  • Custom tools — your own functions, defined with tool() + a Zod schema and bundled with createSdkMcpServer(). They run in-process, so they never leave your app or touch the network unless your code does.
  • External MCP servers — third-party (or your own) servers that expose tools over stdio (a local command) or HTTP. This is how you connect a database, GitHub, Slack, or a filesystem without writing the integration yourself.

Naming & permission is the other half of the story. Every tool from an MCP server — custom or external — is namespaced mcp__<server>__<tool>. Nothing runs unless you allow it: allowedTools auto-approves (wildcards like mcp__github__* work), disallowedTools removes tools, permissionMode sets the default posture, and a canUseTool callback lets you decide per call at runtime. This is your safety dial — a read-only research agent simply never gets Write or Bash.

What makes a tool actually get used? Its description is a prompt aimed at the model — vague descriptions are the number-one reason a tool sits unused. Validate inputs with Zod, return clear structured content, and handle failure by returning a helpful message rather than throwing. And when you need to force the model's hand (say, for structured extraction), the Client SDK's tool_choice lets you require any tool ({ type: "any" }), a specific one ({ type: "tool", name }), or leave it automatic.

Build 1 — drive the built-in tools

Give an Agent SDK query a small scoped toolset and a task that needs several tools, then watch which it reaches for.

import { query } from "@anthropic-ai/claude-agent-sdk";

for await (const msg of query({
  prompt: "Find every TODO comment in this folder, then write them to todos.md.",
  options: {
    // built-in tools, scoped deliberately — no Bash, no network
    allowedTools: ["Glob", "Grep", "Read", "Write"],
    maxTurns: 8,
  },
})) {
  // peek at which tools the agent actually calls
  if (msg.type === "assistant") {
    for (const block of msg.message.content) {
      if (block.type === "tool_use") console.log("→ used", block.name);
    }
  }
  if ("result" in msg) console.log(msg.result);
}
Build 2 — a well-designed custom tool

Note the specific description, the validated input, and the graceful error return instead of a throw.

import { tool } from "@anthropic-ai/claude-agent-sdk";
import { z } from "zod";

const convertCurrency = tool(
  "convert_currency",
  // a description written FOR the model — say exactly when to use it
  "Convert an amount from one ISO currency code to another. Use whenever the user asks to convert money between currencies.",
  {
    amount: z.number().positive(),
    from: z.string().length(3),
    to: z.string().length(3),
  },
  async ({ amount, from, to }) => {
    const rate = await lookupRate(from, to); // your logic
    if (rate == null) {
      // return a helpful message; don't throw — the model can recover
      return { content: [{ type: "text", text: `No rate for ${from}→${to}.` }], isError: true };
    }
    return { content: [{ type: "text", text: `${amount} ${from} = ${(amount * rate).toFixed(2)} ${to}` }] };
  }
);
Build 3 — connect an external MCP server

Wire up a real MCP server over stdio and allow its tools with a wildcard. The filesystem server is a friendly first one.

import { query } from "@anthropic-ai/claude-agent-sdk";

for await (const msg of query({
  prompt: "List the files in my project and summarize what it does.",
  options: {
    mcpServers: {
      filesystem: {
        // stdio: a local command the SDK launches for you
        command: "npx",
        args: ["-y", "@modelcontextprotocol/server-filesystem", process.cwd()],
      },
    },
    // wildcard grants every tool from that one server, nothing else
    allowedTools: ["mcp__filesystem__*"],
  },
})) {
  if (msg.type === "system" && msg.subtype === "init") {
    console.log("tools:", msg.tools.filter((t) => t.startsWith("mcp__")));
  }
  if ("result" in msg) console.log(msg.result);
}
HTTP servers work the same way — swap the command/args for { type: "http", url, headers } and pass secrets via headers or the stdio env field. Remember: MCP tools stay invisible to the model until you list them in allowedTools. "Claude sees the tool but won't call it" almost always means you forgot the allow entry.
Build 4 — force a tool with tool_choice (Client SDK)

Back on the low-level SDK for one exercise: make the model call a specific tool every time — the trick behind reliable structured extraction.

const res = await client.messages.create({
  model: "claude-opus-4-8",
  max_tokens: 1024,
  tools: [extractContact], // a tool whose schema IS your output shape
  tool_choice: { type: "tool", name: "extractContact" }, // force it
  messages: [{ role: "user", content: "Reach me at sam@acme.io or 555-0140." }],
});

Week5

Skills — packaged expertise Claude loads on demand

Use Anthropic's skills, then write your own.

0/6
Learn

A Skill is a folder of instructions (and optionally scripts and resources) that teaches Claude how to do a specific kind of task well — like building a spreadsheet or a slide deck. At its heart is a SKILL.md file with YAML frontmatter: a name, a description (this is what Claude reads to decide when the skill is relevant), and an optional display_title. The magic is progressive disclosure: Claude only pulls the full skill into context when the description matches the task, so you can attach many skills cheaply.

There are two ways to use skills, and it's worth understanding both:

  • Via the Messages API (Client SDK): upload your skill folder as a zip with client.beta.skills.create(), then reference it in the container.skills array. Skills run inside the code execution tool, so you must enable that tool and pass two beta headers: code-execution-2025-08-25 and skills-2025-10-02.
  • Via the Agent SDK: skills load from your project's .claude/skills/ folder. Set the skills option on query() to "all" (or a list of names) to enable them, and make sure settingSources includes "project"/"user" — the most common "my skill isn't loading" bug is forgetting this. A subagent can also preload specific skills through its skills field. Simpler for local development.
Build — write a tiny skill, then invoke it

First, the anatomy of the smallest possible skill. Create skills/commit-style/SKILL.md:

---
name: commit-style
description: Writes git commit messages in our house style —
  imperative mood, under 50 chars, no trailing period. Use whenever
  the user asks for a commit message.
---

# Commit message style

Always use the imperative mood: "Add", "Fix", "Remove".
Keep the subject line under 50 characters.
No period at the end of the subject line.
Leave a blank line before any body text.

Then use a prebuilt Anthropic skill through the Messages API to see the container + beta-header pattern in action:

import Anthropic from "@anthropic-ai/sdk";
const client = new Anthropic();

const res = await client.beta.messages.create({
  model: "claude-opus-4-8",
  max_tokens: 4096,
  betas: ["code-execution-2025-08-25", "skills-2025-10-02"],
  container: {
    skills: [{ type: "anthropic", skill_id: "xlsx", version: "latest" }],
  },
  tools: [{ type: "code_execution_20250825", name: "code_execution" }],
  messages: [{ role: "user", content: "Make a 3-row budget spreadsheet." }],
});
console.log(res.content);
Watch the boundaries. Skills that run via the API execute in an isolated container with no network access and only pre-installed packages. That's a safety feature, not a bug — plan skills to be self-contained. A skill folder must stay under 30 MB uncompressed and its top-level folder name must match the name in SKILL.md.

Week6

Subagents — many specialists, one orchestrator

Isolate context, run work in parallel, and restrict blast radius.

0/6
Learn

A subagent is a separate agent your main agent can spawn to handle a focused subtask. It gets its own fresh context window — it does not see the parent's conversation, and the parent gets back only the subagent's final message, not all the intermediate noise. That buys you four things worth memorizing: context isolation (a research subagent can read 40 files without polluting the main thread), parallelization (independent subagents run at once), specialized instructions (each has its own system prompt and expertise), and tool restrictions (a reviewer can be given read-only tools so it physically cannot edit anything).

You define them programmatically with the agents option on query(). Each entry is an AgentDefinition with a description (tells Claude when to use it), a prompt (its system prompt), and optional tools, model, and skills. Crucially, add "Agent" to allowedTools so the main agent is allowed to delegate without a permission prompt.

Build — a two-specialist code reviewer
import { query } from "@anthropic-ai/claude-agent-sdk";

for await (const msg of query({
  prompt: "Review the auth module for security and test coverage.",
  options: {
    // "Agent" lets the main agent delegate; the rest are for the subagents
    allowedTools: ["Read", "Grep", "Glob", "Bash", "Agent"],
    agents: {
      "security-reviewer": {
        description: "Reviews code for security vulnerabilities. Use for any security question.",
        prompt: "You are a security specialist. Find vulnerabilities and explain the risk. Do not modify files.",
        tools: ["Read", "Grep", "Glob"], // read-only: cannot edit
        model: "opus",
      },
      "test-runner": {
        description: "Runs the test suite and reports coverage gaps.",
        prompt: "You run tests and summarize failures and missing coverage clearly.",
        tools: ["Bash", "Read", "Grep"], // can run commands
      },
    },
  },
})) {
  if ("result" in msg) console.log(msg.result);
}

Claude reads each subagent's description and decides which to call — you can also force one by naming it: "Use the security-reviewer agent to…". Because both subtasks are independent, the SDK can run them in parallel.

Guardrails you'll want early. Once Agent is allowed, Claude decides how many subagents to spawn, and they can spawn their own. Bound a run with maxBudgetUsd (a hard dollar cap) and the env vars CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH and CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS. Set these before you turn an agent loose on a big repo.

Two more things worth trying this week: detecting delegation (watch the message stream for a tool_use block named "Agent") and the filesystem alternative — dropping markdown files in .claude/agents/ instead of defining them in code. Programmatic definitions win if both exist with the same name.

Week7

Capstone — put it all together

One small app that uses custom tools, a skill, and subagents.

0/6
The project

Build a "repo assistant" command-line agent. Given a path to a small project, it should: use a custom tool you wrote (e.g. count lines of code or fetch open TODOs), delegate a security pass and a documentation pass to two subagents, apply a skill that enforces your writing style on the summary it produces, and write a REPORT.md. This deliberately touches every concept from the plan.

Make it real, not just working

The difference between a demo and something you trust is verification and guardrails. Spend the back half of this week here:

  • Verify outputs. Add a check that the report was actually written and is non-empty. For agents that produce data, assert on the shape of the result rather than eyeballing it.
  • Cap spend and turns. Set maxTurns and maxBudgetUsd so a confused agent can't run up a bill or loop forever.
  • Scope permissions. Give each subagent the narrowest tools list that still lets it work. Read-only by default; grant Bash or Write only where genuinely needed.
  • Handle failure. Wrap the query() loop in try/catch and decide what a partial failure should do. Watch the result message's subtype for budget/turn-limit endings.
  • Keep secrets out of git. Confirm .env and any keys are gitignored before you push anywhere.
Stretch goals, if you're enjoying it: add hooks to log every tool call; connect a real external MCP server so a subagent can reach a live data source; or explore sessions to make your assistant resumable across runs.

Glossary — the words that trip people up

Skim this now; come back whenever a term feels fuzzy.

Client SDK vs Agent SDK
@anthropic-ai/sdk is the low-level Messages API client where you write the tool loop. @anthropic-ai/claude-agent-sdk is the high-level library that runs the loop, tools, subagents, and skills for you.
Content block
A response isn't plain text — it's a list of typed blocks. A block can be text, a tool_use request, a tool_result, and more. Understanding blocks is the key that unlocks everything else.
The agent loop
The repeating cycle of: model asks for a tool → your code runs it → you send the result back → repeat until the model gives a final answer. You build it in Week 2; the Agent SDK automates it from Week 3 on.
Tool
A function you expose to the model, described with a name, a description, and a JSON input schema. The model can't run code itself — it asks you (or the SDK) to run tools on its behalf.
Built-in tools
Tools the Agent SDK ships with, the same ones that power Claude Code: Read, Write, Edit, Bash, Glob, Grep, WebSearch, WebFetch, plus orchestration tools like Agent, Skill, and TodoWrite. You enable them by listing their names in allowedTools.
MCP (Model Context Protocol)
A standard way to package and connect tools and data sources. In the Agent SDK you bundle your own tools into an in-process MCP server with createSdkMcpServer(), or connect external MCP servers over stdio (a local command) or HTTP (a URL). Every MCP tool is named mcp__<server>__<tool>.
tool_choice
A Client SDK setting that controls whether the model may, must, or must-not call a tool: { type: "auto" } lets it decide, { type: "any" } requires some tool, and { type: "tool", name } forces a specific one. Handy for reliable structured extraction.
Skill
A folder (anchored by SKILL.md) that teaches Claude how to do a task well. Claude loads the full skill only when its description matches the task — this is called progressive disclosure.
Subagent
A separate agent instance spawned for a focused subtask. It has its own fresh context and returns only a final summary to the parent. Great for isolation, parallelism, and limiting what a piece of the system can touch.
AgentDefinition
The config object for a subagent: description (when to use it), prompt (its system prompt), and optional tools, model, and skills.
permissionMode / allowedTools
How the Agent SDK decides which tool calls run automatically vs. need approval. Add a tool name to allowedTools to auto-approve it — including "Agent" to let the main agent delegate to subagents.
